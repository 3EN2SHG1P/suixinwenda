## 1. 门禁

**后端**（在 `backend/` 下，**不需要数据库服务**）：

```powershell
cd backend
uv run ruff check .
uv run pytest -q
```

测试整体跑在临时目录里的 SQLite 上（`conftest.py` 强制 `DB_BACKEND=sqlite` + 临时 `DATA_DIR`），
绝不连 `.env` 里的真实聊天库；MySQL 方言契约测试只在设了 `TEST_MYSQL=1` 时才跑。

**覆盖率**（CI 强制，本地可选）：CI 的 Ubuntu job 跑的是

```powershell
uv run pytest -q --cov=core --cov=routers --cov=models --cov=tools --cov=schemas --cov-report=term-missing --cov-fail-under=80
```

实测语句覆盖率 85%，门槛 80%。门槛只在 CI 生效：本地单跑某个测试文件时不该因为「没覆盖全项目」而失败。
提交前想确认不会跌破门槛，就跑上面这条完整命令。

**桌面端**（不需要 Electron 二进制，纯 Node）：

```powershell
cd desktop
npm run lint
npm run version:check
npm run check:globals
npm test
npm audit --omit=dev --audit-level=high
```

**覆盖率（只看缺口，不设门槛）**：

```powershell
npm run test:cov
```

只统计被测试真正加载过的模块——`app.js` / `main.js` / `styles.css` 这类没有 unit 测试的文件**不出现在报表里**（不是 0%，别误读成「已覆盖」）。CI 每次 PR 也会跑一次并打进日志，但没有 `--fail-under`：这两个巨块没有测试，设门槛只会逼出为凑数而写的测试；真要提升只能把逻辑从 `app.js` 里拆出来。

**冒烟**（自带假后端，不用起真后端）：

```powershell
cd desktop
npm run smoke
```

以上门禁由 `.github/workflows/ci.yml` 在 push / PR 到 `main` 时自动跑，**Ubuntu 与 Windows 各跑一遍**
（GBK 控制台乱码、文件锁 / VACUUM 事务这类问题只在 Windows 上暴露）。CI 实际执行的是：

- 后端：`uv run ruff check .` + `uv run pytest -q`（CI 另外带上覆盖率门槛，完整命令见本节开头）
- 桌面端：`npm audit --omit=dev --audit-level=high`（运行时依赖漏洞）+ `npm run lint` + **`npm run version:check`**（版本号一致性）+ **`npm run check:globals`**（classic script 顶层声明冲突）+ `npm test` + `npm run test:cov`（只输出报告）
- 另有 Windows job 跑 PyInstaller 打后端，并起 exe 真实请求 `/health`
- MySQL 方言契约只在 Ubuntu 的 job 里跑（Windows runner 不支持 service containers）

**CI 不跑的两项**：`npm run smoke`（需要图形界面）与 electron-builder 出安装包，只能在本地手工执行——
所以 PR 里要自己贴 `[SMOKE] PASS` 作为证据。

**`npm audit` 的两套口径别混**：CI 只拦 `--omit=dev`（随程序运行的依赖）；含 `devDependencies` 的全量审计会报一批
`electron-builder` 依赖链的 moderate，它们不进产物、数量随升级漂移，交由 dependabot 按月跟踪（见 [SECURITY](../SECURITY.md)）。

## 2. 打包

产物在 `desktop/dist/`，文件名是 `SuiXinWenDa-Setup-<版本>.exe`（NSIS 安装版）与 `SuiXinWenDa-Portable-<版本>.exe`
（免安装：不写注册表、可放任意目录，适合 U 盘或没有安装权限的机器），**自带后端**：

```powershell
cd desktop
npm run dist              # 先 PyInstaller 打后端 -> 再 electron-builder 打桌面端
npm run verify:packaged   # 用打包产物起一次后端、跑两个工具子命令（db_info / storage_test）
```

- 打包前会自动校验 `build/THIRD-PARTY-LICENSES.txt` 与当前依赖是否一致：依赖升级后忘了重新生成，
  构建会直接失败并提示跑 `npm run licenses`（`dist:app` 不重装依赖，只检查文件存在）；
- `npm run build:backend`：只打后端，产物在 `backend/dist/suixinwenda-backend/`（onedir）；
- `npm run dist:app`：只打桌面端（改 UI 时快），要求后端产物已存在；
- 后端进包的位置是 `resources/backend/`（exe + `_internal/` + `.env.example`），
  打包态首次启动会把 `.env.example` 复制成 `userData/config.env` 并自动补 JWT_SECRET；
- 安装包因此比「不含后端」的版本大一圈，换来的是免去装 Python / uv 的步骤；
- 自检与多开验证可以设 `SUIXINWENDA_USER_DATA=<临时目录>`，不会碰真实的配置与备份。

**版本号同步**：以 `desktop/package.json` 为唯一来源。`npm run version:sync` 写入另外五处——
`backend/pyproject.toml`、`README.md` / `README.en.md` 的版本徽章、`desktop/src/renderer/views/settings.js`
（设置页「关于」显示的版本）、`desktop/package-lock.json` 的 root version；`npm run version:check` 校验这五处。

`backend/uv.lock` **不在**脚本覆盖范围内：改完 `pyproject.toml` 必须在 `backend/` 下跑 `uv lock`，
否则 CI 的 `uv sync --frozen` 会直接失败（且报错信息不直观）。

## 3. 卸载与清理残留

- 正常情况：`设置 → 应用 → 已安装的应用 → 随心问答 → 卸载`。**常规卸载不会删除你的数据**：
  会话、附件、备份与配置仍留在 `%APPDATA%\suixinwenda-desktop`，重装后自动接上
  （那里是明文聊天记录，模型 Key 已加密；如要彻底清除请用下面的「含本地数据」入口）。
- 开始菜单里另有两个兜底入口，双击即可（会先列清单、要求输入 `yes` 确认）：
  - 「随心问答 - 彻底卸载（保留数据）」：删安装目录 + 注册表卸载项 + 快捷方式，**保留**会话/附件/备份/配置；
  - 「随心问答 - 彻底卸载（含本地数据）」：连 `%APPDATA%\suixinwenda-desktop` 一起删（不可逆）。
- 命令行等价物：`desktop/build/uninstall-clean.ps1 [-Apply] [-PurgeData] [-InstallDir <路径>] [-Yes]`
  （不加 `-Apply` 是干跑，只打印将要删除的内容）。
- 为什么需要它：安装目录一旦被移动或删除，NSIS 的卸载器与注册表入口同时失效，Windows 会退化成
  `msiexec` 并弹出「Windows Installer 用法」帮助页。脚本装在 `%APPDATA%\suixinwenda-desktop\tools\`，
  不随安装目录搬动；重装会覆盖成新版。
- 装在 `C:\Program Files` 下时脚本会**跳过**该目录（需要管理员权限，且误删代价太大）：请改用系统卸载入口。
