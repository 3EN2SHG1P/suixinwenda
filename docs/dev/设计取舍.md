# 设计取舍

> 文档索引：[docs/README.md](../README.md) ｜ 开发者文档：[dev/README.md](./README.md)

改代码**之前**该知道的几条取舍：为什么现在这么写、为什么不能图省事改回去。
排错请看 [踩坑与 FAQ](../踩坑与FAQ.md)，本文件不提供"点哪里"的步骤。

---

## 1. 流式回答按块增量渲染

- 代价最小的做法是每帧对整条回答跑一次 Markdown 全量解析并整体替换 `innerHTML`。但它的成本随回答长度增长，
  而且每帧重建全部节点会把用户手动展开的代码块弹回去、把选中的文字清掉。
- 现在的做法：`renderer/lib/stream-blocks.js` 按空行把回答切成「已闭合块」+「末尾未闭合块」，
  气泡内容拆成两个容器，前缀块插入 DOM 后不再动，每帧只重渲染末尾那段。
- 判据刻意保守：相邻的列表 / 引用 / 表格块**不**算可独立渲染（分开渲染会多出间距或断成两个容器），
  未闭合的代码块一律留在末尾。拿不准就退回全量重渲染——宁可慢一点也不能渲错。
- 因此「改 Markdown 渲染」的正确姿势是改 `markdown.js`（纯净的解析与转义），
  而不是在 `stream-blocks.js` 里加分支。

## 2. 历史图片重放的预算

- 口径：只看最近几轮，并同时限制张数与字节数（`core/context.py` 的 `IMAGE_ROUNDS` /
  `IMAGE_MAX_COUNT` / `IMAGE_MAX_BYTES` / `IMAGE_TOTAL_BYTES`），超预算的降级成 `[图片：文件名]` 占位。
- 图片按 base64 送上游会膨胀，上限要按典型截图校准，不要按极端值估。
- **只放宽轮数不改张数等于没改**：真正的瓶颈是张数与合计字节数，两者必须一起调。

## 3. 上传为什么分块暂存到磁盘

- 直白做法是每个文件 `await file.read()` 全量进内存再生成 base64 块，原始字节与 base64 同时驻留，
  一次传多个大附件时内存会顶上去。
- 现在的做法：`core/files.spool_upload()` 分块写进 `DATA_DIR/tmp` 的一次性目录，超限在写入过程中就中断并删掉半截文件；
  解析时只把当前这一个文件读回内存、解析完立刻释放，落盘阶段再逐个读回；请求结束整目录删除。
- 日志里有一行「附件已分块暂存：N 个文件、X 字节」，出问题时能直接看出走的是哪条路径。
- 因此上限常量集中在 `core/files.py`（`MAX_UPLOAD_BYTES` / `MAX_TOTAL_BYTES` / `MAX_UPLOAD_FILES`），
  不要在路由里另写一份数字。
